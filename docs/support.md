# Support matrix

The aim is one behaviour in every language: each implementation of Bead plays the same conformance files and is proven against the other in the interop. A difference stays on this page only until it closes.

Every cell is read from the tests. A cell that names a test file is supported, and that file, with the `describe` (TypeScript) or the test class or method (C#) named beside it, proves it. "Not tested" means no test holds it, whatever the code does; "not available" means the implementation has no such part. TypeScript test paths are under `implementations/typescript/src/`, C# test paths under `implementations/dotnet/tests/`. The sections of `spec/spec.md` say what each feature is; [the decisions](decisions/README.md) say why it is so.

The cases are the same on both sides: a payload echoed, a string of the length asked, the application's own failure, an unknown procedure and service, an admission that refuses, a resolver that throws, a payload that is not JSON, a call cancelled by its signal and one past its timeout (each cancelled at the server too), a command the server asks, a paced subscription, a session opened and ended, a call presenting the session it learned, a `JWT` presented by default and run in its credential's session, an `ELSEWHERE` carried in `Authorization` over HTTP and failed before it goes over a WebSocket, durations held as section 1.4 holds them, and, over WebSocket alone, 3 MiB each way as transfers. The TypeScript side plays one case more, a subscription that is not paced, and counts more tests than cases, as it splits the echo from the bytes, and the refusals, into tests of their own where the C# side gathers them in theories.
