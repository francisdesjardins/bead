## Context

A service is declared once and served and called in every language: a server where only resolvers
are written, a client that matches it, both over the layer
[0018](0018-a-services-procedures-are-typed-descriptors-served-and-called-through-one-layer.md)
gives each runtime, over any transport, a broker's among them
([0021](0021-a-broker-is-a-transport-and-bead-is-never-a-network.md)). A declaration written
apart in each language drifts as copies do ([0004](0004-one-behaviour-in-every-language.md)); one
written in a language of Bead's own costs every user a grammar. Protobuf's is the one most of them
know, and its tools compile a `.proto` to descriptors, `google.protobuf.FileDescriptorSet`, and
hand a generator a `CodeGeneratorRequest` (`google/protobuf/compiler/plugin.proto`): the stock
generators of each language read the same.

**What the compilers do, measured.** protoc 36.2, protoc 35.1 and buf 1.73.0 give the same services,
methods, types, options and enum values from the same files, on Windows and Linux, in every line
ending. They part on comments and positions: a block comment before a declaration on its own line
is its leading comment in protoc and nothing in buf; protoc on Windows reads a file in text mode and
drops a carriage return (`compiler/importer.cc`:581 at v36.2), where buf and protoc on Linux keep
it; a tab is 8 columns in protoc and 4 in buf, a column a byte in protoc and a terminal cell in buf.
protoc keeps the last of two members of a `oneof` set by two option statements, and drops the first
from the bytes in silence (`descriptor.cc`:9565-9581 at v35.1), where buf refuses every such form
(protocompile's `experimental/ir/lower_options.go`:631-638). protoc reads the first of two copies of
an imported file across its roots, and buf refuses the build. protoc writes a language's code from a
set it did not parse, `--descriptor_set_in`, as it writes it from the `.proto`, the embedded
descriptor aside, which then carries `json_name`. buf 1.73.0 compiles through protocompile's
`experimental` packages at an untagged commit (buf's `go.mod`:22,
`v0.14.2-0.20260910151042-7436f7c76201`), so how it attaches a comment is a version's, not a
standard's.

**What a generator must not do again.** A generator that parses a `.proto` itself, or names a
message by rules of its own in each language, drifts from the stock generators that write the
messages beside it. protoc-gen-es names a message by rules that depend on every name of its file
(`@bufbuild/protoplugin`'s `names.js`:89-111 at 2.16.0): a nested name taken by a top-level
message, a keyword, a name the runtime reserves.

**Where the options' number comes from.** `descriptor.proto` gives custom options two ways: 50000 to
99999 "within a single application or organization, or for experimental options", where nothing
keeps two organizations apart, and a number of protobuf's global registry for options "published
and used publicly by multiple independent entities" (`descriptor.proto`:422-432 at v36.2), which
the registry gives on a pull request or an issue naming the project (`docs/options.md` in
protocolbuffers/protobuf). An organization whose own option holds 58500 on `MethodOptions` cannot
compile a file that imports Bead's at the same number: protoc 36.2 exits 1, `Option "(…)" was
already set.`, and buf 1.73.0 exits 100, `field number 58500 used more than once`.

**Where it reaches.** The constrained C side reads tables generated from a declaration, never a
`.proto` (0017's "a side that keeps no names"). HTTP/JSON transcoding writes one OpenAPI document
for every language from the same declaration, and a request's rules pass through it, under the
feature `validate`
([0035](0035-a-payload-that-reads-is-held-to-its-messages-rules-before-its-resolver-sees-it.md)):
each joins as a feature a reader must know.

### The options weighed

- **A protoc plugin per language**, each with its own front end: the front end written once per
  language, and two languages' readings of one option to keep alike.
- **A front end in C# over Google.Protobuf's descriptors, or in Go over `protogen`**: a toolchain the
  TypeScript side does not have, for the tool both sides use.
- **A front end over protobufjs's parser**, which does not follow protoc's grammar.
- **One front end, TypeScript on Node, over `@bufbuild/protobuf`'s descriptors, writing one blueprint
  every target reads. Chosen.** Node is every contributor's already, for the TypeScript side and the
  root's tools; `@bufbuild/protobuf` reads a set and its options; `@bufbuild/protoplugin` names a
  message as protoc-gen-es does.

Which compiler:

- protoc in the image and buf from npm on Node, a test holding the two to one blueprint: the test
  fails on a same-line block comment, which no rule recovers, and the two paths differ on columns,
  on a copy of `bead/options.proto` and on a `oneof` set twice.
- protoc alone: no binary on npm for every platform, so the repository's own work needs Docker.
- buf alone, and a set another compiler built taken whole: the second compiler comes back as an
  input, with its descriptions, its columns and its `oneof` set twice.
- **buf alone, from the same lockfile on every path, and no set another compiler built; protoc
  writing C# messages from buf's set. Chosen.** One compiler gives one blueprint, one column and one
  refusal wherever beadc runs.

How a procedure's kind and an admission are written in `bead/options.proto`:

- Plain fields, one each held by a rule of `check`: what a set from protoc needs, which beadc does
  not read; a protobuf tool reading the options then sees two optional messages, and a comment says
  the rest.
- **A `oneof`, as `google.api.HttpRule` writes its `pattern` (`google/api/http.proto`:317-338 at
  googleapis `794ca79`). Chosen**: buf refuses a second member in every form, a literal, two
  statements, a literal and a statement, and says "one of" to every protobuf tool that reads the
  file.

How the interop's API is written:

- `interop.proto` alone, beadc writing the blueprint into `spec/`: the spec's input written by the
  product's tool, against [0005](0005-a-toolchain-per-language.md)'s generators of the standard
  library.
- **The blueprint written by hand in `spec/`, `interop.proto` a fixture of the front end whose
  blueprint gives it. Chosen**: the spec keeps its layering, and the interop proves the targets on
  the bytes the conversations play.

Where the format's schema lives:

- In `builder/`, the interop's file referring to it: `spec/check.py`'s rule of one schema a file in
  `spec/schemas/` crossed, and the spec's input held by a schema outside it.
- **In `spec/schemas/`, the format speaking no language. Chosen**: no file option, no rpc name, no
  message a native binding implies; what a front end read of a `.proto` in members a blueprint
  written by hand leaves out. A language that joins changes no schema of the spec's.

## Decision

**beadc compiles with buf, and every decision of Bead's comes from one blueprint.** It compiles a
project's `.proto` roots with buf, `--as-file-descriptor-set`, its imports and source info included,
its own `bead/options.proto` first among the roots, and takes no set another tool built; a blueprint
is taken alone when every binding is native. The front end resolves the set into a blueprint,
`bead-blueprint/1`, and checks it; every target reads its decisions from the blueprint alone, and an
official target reads the set besides for the names of the messages it imports and their files'
options. protoc writes a C# message from buf's set alone, `--descriptor_set_in`, and compiles no
`.proto`.

**A comment becomes a description by one rule.** The leading comment of a service, an rpc or a
failure's value: each line's text after its marker, one space taken off, its end trimmed, carriage
returns read as line feeds; a paragraph's lines joined by one space, paragraphs by a blank line.
Trailing and detached comments are no description, and a comment kept out is written detached. A
target writes a description as its language's documentation escapes it: the TypeScript target
through protoplugin's `f.jsDoc`, a line a line and `*/` written `*\/`; the C# target one `///` a
line, `&`, `<` and `>` escaped as XML, a paragraph a `<para>`, and each character besides LF that C#
reads as a line's end, CR, NEL, LS and PS (ECMA-334's _new-line-character_), as its reference,
`&#xD;` for a CR. The characters XML 1.0's `Char` production leaves out of any document, raw or by
reference, C0's controls but tab, LF and CR, and U+FFFE and U+FFFF, no C# documentation comment
writes: a description holding one is refused, never escaped (`DESCRIPTION_TARGET`), so the two
sides' documentation never differs.

**`bead/options.proto` is the builder's contract.** Package `bead`, C# namespace `Bead.Protobuf`,
one extension on each of `FileOptions`, `ServiceOptions` and `MethodOptions`, at one number a test
holds the three to, protobuf's global registry's from the first publication on
([0008](0008-three-version-axes-and-names-qualified-by-their-owner.md)). `(bead.file)` holds a
file's default admission and its package's retired services; `(bead.service)` a service's id, its
revision, its default admission, its failures' enum, its deprecation's message and its
reservations; `(bead.procedure)` a procedure's id, its kind, its admission, its payload's limit, its
deprecation's message and the failures it lists. A procedure's kind is `oneof procedure_kind`,
`notifies` or `command`, neither meaning a plain request; protobuf-es writes its local name
`procedureKind`, the blueprint's and the runtime's word
([0018](0018-a-services-procedures-are-typed-descriptors-served-and-called-through-one-layer.md)).
An admission is `oneof rule`, `none`, `session` or `hook`, and one that states none is refused
(`ADMISSION_EMPTY`). `bead.Raw`, `bead.Text` and `bead.Json` are the payload types whose bytes are
the payload itself, `raw`, `text` and `json`; any other message is `proto` (spec 17). A payload's
encoding is its message's, and no option names one. A failure's deprecation is protobuf's own
`deprecated` on its enum value, which carries no message: an extension on `EnumValueOptions` would be
a new extendee, for the options' v1 freeze to weigh.

**The blueprint is the runtime's words, resolved, in no language's.** A service's `serviceName`,
`serviceId`, `serviceRevision`, description, deprecation, failures by code, each with its
deprecation when it has one, and reservations; each procedure's `procedureId`, `procedureName`,
`procedureKind`, its `request` and `result` bindings, a `notification` binding exactly when it
notifies, its `admission` as
[0018](0018-a-services-procedures-are-typed-descriptors-served-and-called-through-one-layer.md)'s
`AdmissionRule` writes it, the failures it lists, its `maximumPayloadBytes` and its deprecation when
it has them. A binding is its encoding, and for `proto` alone its message's full name. What a front
end read of a `.proto` — its files and packages, the messages a `proto` binding names and, under the
feature `validate`, the fields of a request's message that hold a rule or lead to one, each with its
rules in protovalidate's own shape, a service's file and full name — sits in `proto` members, which
a blueprint written by hand leaves out. Beside them, under no feature, each procedure's `http`, its
`google.api.http` rules, each of its `additional_bindings` a rule of its own in their order, and its
`idempotency_level`, the `.proto`'s words resolved; every field of every message a binding names or
a field of one reaches, by its name, number, JSON name, type, label, key, presence and `oneof`, a
field of `LEGACY_REQUIRED` presence marked `legacyRequired: true` under the feature
`legacy-required`, its presence `explicit`, of no label and no `oneof`, which every target and the
document generate ([0042](0042-a-proto-message-that-leaves-a-required-field-unset-neither-reads-nor-writes-and-a-gateway-refuses-it-where-its-server-would.md)), and the enums they name, each value by its name and number, aliases in their order; a well-known type by
its full name alone. A procedure's default routes are no member: beadc derives them, its prefix
`beadc.yaml`'s, so a blueprint written by hand, its bindings all native, has them with nothing
written
([0037](0037-a-procedure-is-also-an-http-route-which-a-gateway-answers-as-one-more-client-of-its-server.md));
each path among them is a path from its root, as an import names it, parts by `/`, none `.` or `..`,
which the schema holds and `PROTO_FILE` holds to a file `proto.files` lists, as protoc's plugin
protocol holds a file's name. No language's option and no rpc's name: a C# namespace is the set's
`csharp_namespace`, which `check` refuses where it is no C# namespace, identifiers of ASCII letters,
digits and `_` joined by dots, `CSHARP_NAMESPACE`, since the C# target writes it as it is and
anything else would be the `.proto` author's code in every consumer's build; or, for a blueprint
alone, the output's `namespace` in `beadc.yaml`, held to the same form; and an rpc's name is its
procedure's with the first letter raised. No default and no inheritance: a file's and a service's
admission is resolved into each procedure. Nothing of configuration: no credential, no window, no
limit of a router's, no topic. `format` names the major, which a reader refuses when it does not
know it; `requires` lists the features a blueprint uses beyond its major, which a reader refuses
when it does not know one, as JOSE's `crit` does
([RFC 7515 §4.1.11](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.11)), and each target
declares the features it generates, `beadc generate` refusing one that lacks a feature its blueprint
requires, `FEATURE_UNGENERATED`; removing a member, or changing its meaning, makes `/2`. `requires`
names what a target must play, a rule unplayed letting through what a server must refuse, and never
what a target may leave unserved, as a route is, which refuses what no client was promised. Adding a
member is a minor of `bead-blueprint/1` that every older reader refuses by its schema,
`additionalProperties: false` on each of its objects, before it reads `requires`: fail-closed, a
blueprint written by hand held as strictly as the schema holds it. `specVersion` names the version
of `spec/spec.md` whose sections 16 and 17 its producer follows. Its schema,
`spec/schemas/bead-blueprint.schema.json`, is the format, a description on every member.

**A blueprint has one form.** Its members sorted as RFC 8785 sorts them, by their names' UTF-16 code
units; its strings escaped as RFC 8785 escapes them
([§3.2.2.2](https://www.rfc-editor.org/rfc/rfc8785#section-3.2.2.2)), never a surrogate alone,
which I-JSON forbids ([RFC 7493 §2.1](https://www.rfc-editor.org/rfc/rfc7493#section-2.1)); its
numbers integers, never with a fraction or an exponent; two spaces of indentation, a final line feed,
UTF-8 without a byte order mark; its arrays sorted by identity: files by path, messages by full name,
services by id, procedures by id, failures by code, a procedure's failures in their codes' order,
ranges ascending, names in their code points' order. beadc writes every blueprint in its form,
and refuses one that I-JSON forbids; `beadc blueprint --check` and `spec/check.py` hold one to its
form.

**The unit of generation is the service**, and one blueprint is one id space. A service gives
`<Name>Procedures`, `<Name>Failures`, `<Name>Server`, `<Name>Client`, `<Name>Admissions` and
`<Name>Windows`, its name its `.proto` name with a trailing `Service` taken off; in TypeScript also
`<Name>Resolvers`, and `<Name>ServerOptions` and `<Name>ClientOptions`, the layer's options named
for the service, which C# names `ServiceServerOptions<<Name>Procedures>` and
`ServiceClientOptions<<Name>Procedures>`; in C# also `<Name>Commands`, `<Name>Notifiers` and
`<Name>Notifications`, the classes of a server's `Command` and `Notify` and of a client's
`Notifications`; on the C# side, a procedure that lists failures gives a class of them, nested in
`<Name>Failures` under its rpc's name, and every type that holds a member a procedure or a hook
names is a sealed class of `init` properties, which synthesizes no member. A procedure's name is its
rpc's, the first letter lowered (spec 16.4); a failure's is its enum value's, the enum's prefix
taken off. A name that collides with a member any official target generates, or with the class it
sits in, or a class name a message or a public type of the runtime holds, or a message or an enum of
the C# namespace it is written in, in any file of the set that shares the namespace, is refused,
never escaped (`NAME_TARGET`): the rule runs on the blueprint, and on a `.proto` for the messages
and enums of each C# namespace, which a blueprint does not hold, over every official target, so one
blueprint has one verdict whatever targets a project names.

**A target writes data and types; behaviour is the runtime's.** A generated file holds the service's
descriptors, made by `requestOf` and `commandOf`, `RequestProcedure` and `CommandProcedure`; its
catalogue; and a server class and a client class, each a thin shell over `createServiceServer` and
`createServiceClient`, `ServiceServer<TService, TData>` and `ServiceClient<TService>`. A server
class is offered on one Bead server; it takes the layer's options, required when a procedure names a
hook, and when none does, optional in TypeScript and in C# a constructor of their own beside one
that takes none. A client class takes its Bead client, then the layer's options, optional; it holds
a requester of each procedure its server answers, under the procedure's name, its notifications
under `notifications`, at the windows its caller gives, unpaced by default
([0002](0002-a-subscription-goes-at-its-clients-pace.md)), and `on` for the commands it answers. A
file names the contract it needs, `GENERATED_CODE_SUPPORTS_VERSION_6` or
`GeneratedCode.SupportsVersion6`, and a route table 5, `./transcoding`'s
`GENERATED_CODE_SUPPORTS_VERSION_5` or `GeneratedCode.SupportsVersion5`, the runtimes carrying both
([0018](0018-a-services-procedures-are-typed-descriptors-served-and-called-through-one-layer.md)); a
service's file imports nothing of Bead's but `./service`, and `./proto` where it binds `proto`, a
route table `./transcoding`, each from a path relative to its output's folder or a package's name;
the C# it writes qualifies every type as `global::Bead.` and `global::`, and a project whose code
binds `proto` references `Bead.Protobuf`, whose `ProtoCodecs.Of` is its codec, as the TypeScript
codec is `protoCodecOf` of `./proto`, each checking a payload's records before its stock library
reads them
([0028](0028-a-proto-payloads-records-are-read-against-its-message-before-its-library-reads-them.md))
and judging its required fields ([0042](0042-a-proto-message-that-leaves-a-required-field-unset-neither-reads-nor-writes-and-a-gateway-refuses-it-where-its-server-would.md)).
The TypeScript target runs on `@bufbuild/protoplugin`, in beadc's process, its `target=ts`, its
header written above protoplugin's imports, never its preamble, its imports printed as symbols. A
service with no `proto` member is written at the folder's root under its name; one with a `proto`
member at its file's path, whichever the source, as protoc and buf write a file at the path its
descriptor names. The C# target is a printer of its own, in beadc's process, and names a message
from its descriptor; it writes a service with a `proto` member in its namespace's folder at its
file's name, beside protoc's file, protoc run with `base_namespace=`, the namespace the set's
`csharp_namespace` from a `.proto` and the output's `namespace` from a blueprint, and one with none
at the output's root, under its name, in the output's `namespace`. A deprecation marks what each
target writes for it, `@deprecated` and `[Obsolete]` with one text and `BEAD0001` in C#; a C# file
silences its own uses in every file, protoc's `#pragma warning disable`, and a TypeScript file where
it marks one or names a deprecated message, protoc-gen-es's `/* eslint-disable */`, which
protoc-gen-es writes in every file: the TypeScript side's lint holds beadc's output to its rules
wherever nothing is marked. `generate` refuses two files it would write at one path, over every
output, the paths compared case-folded. It removes nothing unless `beadc.yaml` sets `clean`, buf's
opt-in, protoc never removing a file. Without `clean`, a `_bead.ts` or a `*Bead.cs` under beadc's
own header that the source no longer gives, which nothing but beadc writes, is named by `generate`
and left, and fails `generate --check`, so a service a source dropped never ships in silence; a file
under protoc's or protoc-gen-es's header, a project's own as much as beadc's, is not named. Under
`clean` it takes out of each output's folder a file of a kind it writes that this run does not, read
by its first lines in both targets, a `_bead.ts` or a `*Bead.cs` with beadc's header, a `_pb.ts`
with protoc-gen-es's, a `.cs` with protoc's at the path protoc gives its source, and prints each:
under `clean` the generated files' kinds in an output's folder are beadc's alone, and a project's
own files stay, where buf's `clean` empties the folder. Messages are the stock generators' —
protoc-gen-es with `erasable_syntax=true`, run in beadc's process, and protoc's C# generator over
buf's set — or `external`, a project's own generator writing them. An output with `http: true`, as
`keepValidateOptions` is an output's, writes its route table and its HTTP client
([0037](0037-a-procedure-is-also-an-http-route-which-a-gateway-answers-as-one-more-client-of-its-server.md)),
and embeds the OpenAPI document byte for byte, the one `beadc.yaml`'s `openapi:` writes of the
blueprint, in the blueprint's own form; any other writes neither and embeds nothing, so no assembly
carries a document it never serves, and a target that generates no HTTP is refused such an output,
`HTTP_UNGENERATED`.

**Generated code passes its language's gates but its formatter.** `*_bead.ts` passes oxlint, its
type-aware half included, and the types, and stays out of oxfmt; the C# passes the build's
analyzers, code style and doc comments, and `dotnet format` leaves its folder out. Each target marks
its file generated in its language's word, `// @generated` in TypeScript, its first line, and
`// <auto-generated/>` in C#, its header's last, then `#nullable enable`, which a file so marked
needs; where Bead's gates judge it, their configuration says so, `[*Bead.cs]`
`generated_code = false` in the C# side's `.editorconfig`; it writes a doc comment on every public
member either way.

**`beadc check` refuses by rule name**, at three levels: on a `.proto` input, on any blueprint, a
hand-written one included, and in each target. A finding prints as
`file:line:column: severity RULE: message`, in text, JSON or GitHub's format, a blueprint's at its
JSON Pointer ([RFC 6901](https://www.rfc-editor.org/rfc/rfc6901)); a warning is left out by its
name, an error never is. The rules, their levels and their reasons are `builder/README.md`'s, each
with its cases in `builder/`.

**`beadc breaking` compares two blueprints by id**, against the last release that carries one
([0017](0017-ids-are-for-life-and-a-procedures-name-takes-one-ascii-form.md)), in two categories,
`WIRE` within `API`: `WIRE`, a peer built from the last release still talks with one built from
this one; `API`, besides, code written against the last release's generated API still compiles and
means the same, and so do the metrics and filters that name a procedure. A hook a service's
procedures name, added or gone, is `API`, since its server's options name each; a service or a
procedure gone, deprecated, then its id reserved, passes `WIRE` and not `API`, since its generated
code goes with it; a name stays its id's or is reserved; a revision is never lowered, and moves
where its service changed, a message its bindings reach included. buf's own rules compare the messages of two buf images, `WIRE`'s or
`FILE`'s, its rules keyed by a service's or an rpc's name excepted and `bead/options.proto` ignored.
`--against` names a folder, its committed blueprint read for Bead's rules, an archive on standard
input, or a blueprint; the earlier is read, never judged by later rules, and a committed blueprint
its `.proto` contradicts, compared by id, or one named and missing, is `AGAINST_BLUEPRINT`'s
warning. The wrappers' `--against-ref` pipes the project's `git archive` at a ref into the run. A
finding is placed by its pointer, where a reviewer reads it, and names its subject, its entity by
ids: AIP-122's hierarchy of kinds and ids, `service:1/procedure:4`, written `kind:id` so that it
never reads as the index pointer it replaces, which AIP-122's `services/1/procedures/4` would match
once its slash is dropped. A finding is waived by its rule's name, scoped to its subject, by ids,
which no shift of an array moves, or to its file; a waiver of a breaking rule or of buf's that names
neither, which would waive a later change's finding too, is refused, as ESLint's
`no-unlimited-disable` refuses a disable that names no rule, and so are a scope that is a pointer
and no subject of its rule's kind; a waiver that waived nothing is `WAIVER_UNUSED`'s warning.

**The interop's API is its blueprint, and its behaviour `interop-service.json`'s.**
`spec/interop-blueprint.json` is written by hand, in the blueprint's form, under `specVersion`: the
service's id and revision, and each procedure's id, kind, bindings, admission, failures and one line
of description; `tools/release.mjs` moves its `specVersion` as it moves every conformance file's
that repeats one ([0008](0008-three-version-axes-and-names-qualified-by-their-owner.md)). Its schema,
`spec/schemas/interop-blueprint.schema.json`, is the format's with `requires` empty and one service:
the generators and both sides' interop read that one service and no feature, and the day one reads a
feature, it lifts the pin.
`spec/interop-service.json` states, for each of those procedures by its name and in
their order, what it takes, what it answers, what it admits where its admission is not `none` and
what it notifies where it notifies, beside its relay and its credentials. `spec/check.py` holds the
blueprint to its schema and its form, and the two files to one list, and `--write-blueprints` lays the
blueprint out in its form, its arrays sorted, which an author edits as they like; it writes nothing
when a string holds a surrogate alone, and it never shortens the file it fails to write. The fixture
`builder/test/fixtures/bead/interop/v1/interop.proto` gives a blueprint whose projection, its `proto`
members left out, is the spec's byte for byte, which beadc's tests hold. Each side's interop code is
generated from the blueprint; the handlers and the credentials are written.

**Where each lives.** The builder in `builder/`, with a toolchain of its own
([0005](0005-a-toolchain-per-language.md)); `bead/options.proto` in `builder/proto/`; the format's
schema and the interop's blueprint in `spec/`; the rules, the name rules of a blueprint that section 16
leaves to the builder, and what each option means, in `builder/README.md`; the repository's own
`beadc.yaml` at the root. beadc builds into an image, `ghcr.io/francisdesjardins/beadc`, for
linux/amd64 and linux/arm64, each built and tested natively in CI, from `builder/Dockerfile` on a
Node base pinned by its digest, and tested on itself: Node, beadc as `builder/` holds it with its
production packages, buf, protoc-gen-es, protoc at its pin with its well-known types,
`bead/options.proto`, the files of `spec/` beadc reads at their places beside it, and the licence
texts of what it adds to its base; no SDK. Its own user is not root; the wrappers `beadc.sh`
and `beadc.ps1`, which `beadc wrapper` prints, `beadc init` writes and a project commits, run it as
the caller, as the container's root under a rootless engine, whose root is the caller, without a
network, its root read-only, under an init that passes a signal on, and pass it the arguments as the
shell hands them, one engine call from both; and beadc runs from `builder/` on Node, which is how
the repository uses it.
`beadc init` writes a project's starter: `beadc.yaml` at its root, its `.proto` under `proto/`, a
package a folder, and each language's generated code under that language's own folder,
`typescript/gen` and `dotnet/gen`. A generated file resolves what it imports from where it sits, so
a `package.json` at the project's root or in its language's folder serves it, and the .NET SDK's
default items compile it from a project in either place. `examples/hello` is that starter, each
output split by its messages, beadc's or the project's own build's.

**What a peer receives does not change.** No envelope, no code, no conversation: ids travel, names
never; a payload's bytes are its encoding's (spec 17).

## Consequences

**A `.proto` is compiled by buf, whatever compiler its team uses.** buf refuses what protoc lets by:
a member of a `oneof` set twice, a copy of an import in two roots. A team whose build runs protoc
hands beadc its `.proto` roots, never its set; a set taken whole is an addition, under `requires`
if it reaches the blueprint, and a buf image alone.

**A buf upgrade can move a description.** Descriptions are part of a blueprint, and buf attaches a
comment through an `experimental` package; the comments fixture, leading, trailing, detached and
multi-paragraph comments, CRLF and a byte order mark, is beadc's golden test of buf's attachment, so
an upgrade that moves one fails it before a user's blueprint moves.

**Two copies of the options' C#, loaded in one process, clash** through Google.Protobuf's extension
cache, keyed by file name (`FileDescriptor.cs`:529-548 at v3.36.2): two libraries, each built with
generated messages and its own copy, make the second's `GetExtension` over Bead's options throw.
Generated code reads no option at run time, so only a user's own reflection meets it. The way out —
one public copy in a package of its own, `DisableExtensionCaching`, or edition 2024's `import option`
— is decided with the options' freeze.

**The interop is stated in two files and declared in a third.** Its API in the blueprint, its
behaviour in `interop-service.json`, which `check.py` holds to one list of names; the fixture
declares the API again, each description a one-line comment, held equal by beadc's tests. Adding a
procedure is three edits.

**The spec's axis carries the builder's format, and no language's.** Its schema is under
`spec/schemas/`, so a change to the format moves the spec's version as any file's does
([0008](0008-three-version-axes-and-names-qualified-by-their-owner.md)); a target's option, a C#
namespace or a Go package, is `beadc.yaml`'s or the set's, never the format's.

**A blueprint is laid out by `spec/check.py`, never by the root's formatter.** oxfmt 0.71.0 writes a
short array on one line, where the form writes one member a line, so the root's format step and a
release's leave `spec/interop-blueprint.json` out, and `check.py` holds its form instead.

**A blueprint is refused for a target it does not use.** `NAME_TARGET` reads every official target's
names, and a description a target cannot write is refused alike, `DESCRIPTION_TARGET`, so a project
that generates TypeScript alone is refused a procedure named `all`, a C# collision; the names a
target reserves are listed in `builder/README.md`, and a target that joins adds its own to every
blueprint's verdict.

**Adding a hook breaks every construction of its server**, as a required option does in any API:
`beadc breaking` names it, and the release says it.

**A deprecation carries a text where protoc's marks are bare.** Without the blueprint's message, it
reads `No replacement is named.`, in `@deprecated` and in `[Obsolete]` alike: CA1041 asks a message
of the C# side's gate, and the two targets read alike. A deprecation is a warning at each use of a
marked declaration, the caller's and the implementer's, who still serves the procedure: `BEAD0001`
in C#, an error under `TreatWarningsAsErrors` that `WarningsNotAsErrors` keeps Bead's alone a
warning, and `no-deprecated`'s in TypeScript, which its `allow` scopes; tsc says nothing. It is the
warning period SemVer asks for, ahead of the release that takes the declaration out, which `API`
holds.

**One toolchain more.** `builder/` has its own lockfile, its own vendored Yarn and its own CI job,
on Linux and Windows; its install fetches buf's binary for its platform, about 105 MiB on Windows.

**The image weighs 128 MB compressed** on amd64, 405 MB on disk: Node 26's binary is 143 MB of it,
buf's package 106 MB, protoplugin's TypeScript 32 MB.

**`erasable_syntax` is protoc-gen-es's experimental option**, and its output needs
`@bufbuild/protobuf` 2.13.0 or later, which the header names; the image pins protoc-gen-es, and
beadc's golden tests catch a change of it.

**protoc is one pin, which beadc holds.** protoc's version, and the oldest Google.Protobuf its code
needs, are one pin, `builder/protoc.json`, beside each archive's sha256, which beadc holds and the
image and CI read; the header names both. beadc looks for protoc only when it writes a C# message,
and refuses another version, exit 2, naming both: Grpc.Tools' protoc, which the C# side's build
runs, writes the same code under another header line, so `generate --check` would fail with nothing
changed. A contributor who generates C# messages fetches the pinned one,
`builder/tools/fetch-protoc.mjs` checking its archive's sha256 before it extracts it, and names it by
`BEADC_PROTOC`.

**Its gates** ([0006](0006-a-rule-has-its-gate.md)): the `spec` job holds the interop's blueprint to
its schema and its form, and `interop-service.json` to its procedures; the `builder` job runs
beadc's tests on Linux and Windows, `beadc check` and `beadc blueprint --check` over the interop's
blueprint, `beadc generate --check` over the repository, `buf lint` and `buf format` over
`builder/proto` and the fixtures, the image's test stage and the wrappers' tests, and on the
image's legs `beadc generate --check` over the repository and `examples/hello` through each
wrapper; each side's job holds its generated code to its gates and the interop both ways, and the
`dotnet` job builds the C# goldens as a consumer does, each use of a marked declaration
`BEAD0001`'s; the
`examples` job holds every example's copies and wrappers, holds `examples/hello` to what beadc
generates and its `.proto` to buf's lint and layout, builds each half with its messages generated
and external, and plays each client against each server; the `builder` job holds the interop's
blueprint and `examples/hello` to the last release, the newest whose commit is not HEAD's, by
`beadc breaking`, every warning failing; the `commits` job holds
`tools/release.mjs`'s move of its version, through the root's
tools' tests. A gate here that does not run is among 0006's gates owed.

**`beadc breaking` holds against the last release**: that release carries the interop's blueprint
and `examples/hello`'s, and one without a blueprint, or none found, fails the step, so it never
passes by comparing nothing.
