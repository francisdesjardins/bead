# hello

A project written as a consumer writes one: one `.proto`, [`proto/hello/v1/hello.proto`](proto/hello/v1/hello.proto),
its service generated by beadc in TypeScript, in C# and in Rust, and in each language a server and
a client where only the resolvers, the hook and the calls are written. The three halves are one
program: the same procedures, the same resolvers, the same failures and the same hook, and each
client writes the same lines, [`transcript.txt`](transcript.txt), against any server.

`HelloService` holds what a service declares: `proto` messages; `sayHello`, which fails with a
failure of its catalogue, `NAMELESS`, and, given no name, asks its caller's by `askName`, a command
the client answers; and `countDown`, whose request a rule of its `.proto` holds to 10 at most,
notifies a `Tick` a step to a client that asks for them at a window of 1, and is admitted by its
hook, `greeted`, once the connection said hello. Every half serves and calls it over WebSocket,
and serves it over HTTP too, by a gateway on a port of its own: one server, `HelloService` offered
on it once, takes its connections from its WebSocket transport and from an in-memory one, joined,
which the gateway crosses as one more client of it, one Bead connection an HTTP exchange
([`spec/transcoding.md`](../../spec/transcoding.md)).

A rule is protovalidate's, `[(buf.validate.field).int32.lte = 10]`, which beadc compiles into each
half's validator: the server judges every request once it reads, before its resolver, and answers
one its rules refuse `PAYLOAD_INVALID`, its violations in its detail (spec 18). beadc compiles
protovalidate's standard rules on a field, a `oneof` and a message, and refuses the rest, CEL among
them, by `beadc check`. A rule judges the payload alone: what needs the session, as the name a
nameless caller gives when asked, stays its resolver's, which answers `NAMELESS`.

Its servers listen on `127.0.0.1`, the address each is given, where a server given none listens on
`localhost`, both loopbacks, and name no hosts: every server takes `127.0.0.1`, which its clients
connect to, and refuses a page that rebinds its name to it (spec 15.12).

```
countDown before sayHello: ACCESS_DENIED, say hello first
sayHello Bead: Hello, Bead!
sayHello, nameless: Hello, Ada!
countDown from 11: PAYLOAD_INVALID, {"bounds":{"lte":10},"fieldPath":"from","message":"must be less than or equal to 10","ruleId":"int32.lte"}
{"more":0}
countDown from 3: 3 2 1 0, one at a time
sayHello, nameless again: NAMELESS, nobody to greet
POST /api/Hello/sayHello {"name":"Ada"}: 200 application/json, {"greeting":"Hello, Ada!"}
POST /api/Hello/sayHello {}: 500 application/problem+json, {"code":64,"scope":"protocol","status":500,"title":"PROCEDURE_FAILED","type":"tag:francisdesjardins.ca,2026:bead/PROCEDURE_FAILED"}
POST /api/Hello/countDown {"from":11}: 403 application/problem+json, {"code":33,"detail":"say hello first","scope":"protocol","status":403,"title":"ACCESS_DENIED","type":"tag:francisdesjardins.ca,2026:bead/ACCESS_DENIED"}
POST /api/Hello/countDown {"from":3}: 403 application/problem+json, {"code":33,"detail":"say hello first","scope":"protocol","status":403,"title":"ACCESS_DENIED","type":"tag:francisdesjardins.ca,2026:bead/ACCESS_DENIED"}
GET /openapi.json: 200 application/json, gen/openapi.json, beadc's, byte for byte
```

The hook's refusal and its detail; a request and its answer; the server's command to its client
before it answers, the client answering `Ada`; a request its rule refuses, its detail as it came,
a violation a line of canonical JSON, then the count of those it left out; the four ticks in their
order, and how many of the client's callbacks ran at once, each holding itself 10 ms: at a window
of 1, one, and without it, the ticks overlap; then the catalogue's failure by its name, the client
answering an empty name the second time it is asked.

Then what a person asks the gateway with curl, each request its own exchange and its own Bead
connection, which ends with it, as `docs/support.md`'s "Leveled down" has it: a greeting, its
result as JSON; one given no name, whose command `askName` the gateway's connection answers
`SERVICE_UNKNOWN`, since an HTTP exchange has no way back to its caller while its request waits,
so its resolver fails, `PROCEDURE_FAILED`, 500, the server writing that line to its standard error;
a count past its rule and one within it, both refused by the hook, `ACCESS_DENIED`, 403, before the
rule is judged, since no exchange's connection was ever greeted, a connection's session ending
with its exchange; and the document, as beadc wrote it. Each failure is a problem, RFC 9457's, its
type a `tag:` URI of its code.

## Generating

`generate` writes what beadc generates from `beadc.yaml`, and `generate --check` finds nothing to
change. In this repository, beadc runs on Node, or from an image built here, which `BEADC_IMAGE`
gives the wrappers in place of the one they name:

```sh
# beadc on Node, from the repository: protoc and protoc-gen-buffa at their pins, then beadc
export BEADC_PROTOC="$(node ../../builder/tools/fetch-protoc.mjs)"
export BEADC_PROTOC_GEN_BUFFA="$(node ../../builder/tools/fetch-protoc-gen-buffa.mjs)"
node ../../builder/src/cli.ts generate
node ../../builder/src/cli.ts generate --check

# or the image built here, through the wrappers
docker build -f ../../builder/Dockerfile -t beadc:local ../..
BEADC_IMAGE=beadc:local ./beadc.sh generate
```

```powershell
# the same, in PowerShell 7.6
$env:BEADC_PROTOC = node ../../builder/tools/fetch-protoc.mjs
$env:BEADC_PROTOC_GEN_BUFFA = node ../../builder/tools/fetch-protoc-gen-buffa.mjs
node ../../builder/src/cli.ts generate

docker build -f ../../builder/Dockerfile -t beadc:local ../..
$env:BEADC_IMAGE = 'beadc:local'; ./beadc.ps1 generate
```

Given no `BEADC_IMAGE`, the wrappers run the image they name, as the engine finds it:

```sh
./beadc.sh generate            # or ./beadc.ps1 generate, in PowerShell 7.6
./beadc.sh generate --check    # nothing to change
```

`generate` also writes `.beadc/include/bead/options.proto`, Bead's options,
`.beadc/include/buf/validate/validate.proto`, protovalidate's, and
`.beadc/include/google/api/http.proto` and `annotations.proto`, googleapis', which git ignores: the
copies an editor reads, and the ones each half's own generator reads where its messages are
external.
Run `generate` once in a fresh clone before an external build.

## Building and running

The TypeScript half, on Node 24.9 or later:

```sh
cd typescript
yarn install --immutable
yarn check                # types in both modes and as a consumer, lint, format
yarn build                # dist/generate/hello.mjs: the messages beadc generated
yarn build:external       # dist/external/hello.mjs: the messages buf generate writes with protoc-gen-es
node dist/generate/hello.mjs serve        # {"port":n,"gateway":m}, then serves until its input ends
node dist/generate/hello.mjs call <port>
```

The C# half, on the .NET SDK `global.json` names:

```sh
cd dotnet
dotnet build                                # bin/generate/: the messages beadc generated with protoc
dotnet build -p:HelloMessages=external      # bin/external/: the messages Grpc.Tools writes from the .proto
dotnet bin/generate/Debug/net10.0/Hello.dll serve
dotnet bin/generate/Debug/net10.0/Hello.dll call <port>
```

The Rust half, on the toolchain its `rust-toolchain.toml` pins, the Rust side's. Its two modes are
two binaries over one target folder; the feature `external` builds the second, whose build script
runs buf over hello's workspace, the one `BUF` names or `buf` on the path, then
`bead_protobuf_build::config_of` over the set buf writes, which nobody commits:

```sh
cd rust
cargo build --locked                                    # target/debug/hello: the messages beadc generated with protoc-gen-buffa
BUF=../typescript/node_modules/.bin/buf cargo build --locked --features external
                                                        # target/debug/hello-external: the messages its build script writes
target/debug/hello serve                                # {"port":n,"gateway":m}, then serves until its input ends
target/debug/hello call <port>
```

Each half takes `serve`, `serve <port>` or `call <port>`, a port its digits alone, at most 65535,
and refuses any other arguments with its usage, exit 2. Each half in both modes built,
`node pairs.mjs` plays each client against each server, thirty-six pairs, then asks that server's
gateway: a pair passes when its client exits 0 and what it writes, then the gateway's answers, are
`transcript.txt` byte for byte, its server exits 0 once its input ends, the client writes nothing
to its standard error, and the server only the line of its nameless gateway call. The
Rust binaries are read from `rust/target/debug/`, or from `CARGO_TARGET_DIR`'s `debug/` where it is
set; `HELLO_RUST`, set to anything but `built`, leaves their pairs out. CI's `examples` job runs all
of it on Node 26, and on 24.9, the floor the TypeScript half declares, the TypeScript and C# halves
alone, sixteen pairs.

## Calling with the generated HTTP client

Use the `gateway` port a server prints. Each output has `gateway: {}`, so its route table also
exports `HelloHttpClient`. In the TypeScript project, a source file calls it with fetch:

```ts
import { HelloHttpClient } from '#hello/http';

const hello = new HelloHttpClient('http://127.0.0.1:8080');
const answer = await hello.sayHello({ name: 'Ada' });
console.log(answer.greeting);
```

In the C# project, the same call uses HttpClient through `Bead.Transcoding`:

```csharp
using Hello.V1;

using var hello = new HelloHttpClient(new Uri("http://127.0.0.1:8080"));
var answer = await hello.SayHello(new SayHelloRequest { Name = "Ada" });
Console.WriteLine(answer.Greeting);
```

In the Rust project, the same call goes through Bead's HTTP caller, under the core's feature
`gateway`, its output's `bead_http`:

```rust
use bead::{HttpCallOptions, HttpCallerOptions};

use crate::generated::bead_http::HelloHttpClient;
use crate::generated::messages::hello::v1::SayHelloRequest;

let hello = HelloHttpClient::new("http://127.0.0.1:8080", &HttpCallerOptions::default())?;
let request = SayHelloRequest { name: "Ada".to_owned(), ..SayHelloRequest::default() };
let answer = hello.say_hello(&request, &HttpCallOptions::default()).await?;
println!("{}", answer.greeting);
```

Replace `8080` with that gateway port. Each call uses its default POST route, and a problem throws
`FailureError` or `FailureException` with its Bead code and scope, or, in Rust, is the `CallError`
its future gives. A notifying procedure exposes `hello.subscribeCountDown({ from: 3 })`,
`hello.SubscribeCountDown(new CountDownRequest { From = 3 })` or
`hello.subscribe_count_down(&request, &options)`, an async sequence of its result then
notifications, in Rust a `Stream`. This service's `greeted` hook refuses that HTTP subscription:
each exchange has its own Bead connection, and a greeting on another exchange greets another
connection. A name must be given to `sayHello`, since HTTP answers no `askName` command.

## What a project outside this repository writes instead

The example reaches each runtime from its source, as no runtime is published: the TypeScript half by
Yarn's `portal:` protocol, the C# half by a `ProjectReference` of each assembly it uses,
`Bead.Transcoding.Http`, its gateway's, and `Bead.Protobuf`, whose check its generated `proto`
codecs call, among them, and the Rust half by a `path` of each crate it uses. A project of its own
names each runtime as a package, by its name and a version: `"@francisdesjardins/bead": "<version>"`,
`<PackageReference Include="FrancisDesjardins.Bead.Transport.WebSockets" Version="<version>" />`,
`<PackageReference Include="FrancisDesjardins.Bead.Transcoding.Http" Version="<version>" />` and
`<PackageReference Include="FrancisDesjardins.Bead.Protobuf" Version="<version>" />`;
`bead = { package = "francisdesjardins-bead", version = "<version>", features = ["websocket", "gateway"] }`,
`bead-protobuf = { package = "francisdesjardins-bead-protobuf", version = "<version>", features = ["transcoding"] }`, Buffa's
`buffa` and `buffa-descriptor` at the one version its messages are generated for, `=0.9.2`, and,
for messages its build writes, `bead-protobuf-build = { package = "francisdesjardins-bead-protobuf-build", version = "<version>" }`
among its build dependencies.

The Rust half mounts each output by its root, `#[path = "generated/generate/mod.rs"] pub mod generated;`,
public, as its lints, the Rust side's, ask of a binary; a project under Rust's default lints
writes `mod generated;`. In the crate that mounts them, the generated options are built by a
literal over their `Default`, `HelloClientOptions { windows: …, ..HelloClientOptions::default() }`,
where clippy's `field_reassign_with_default` refuses the assignment form.

From source, the TypeScript runtime is its `.ts` files, which a consumer's compiler compiles under
the consumer's options. [`typescript/tsconfig.consumer.json`](typescript/tsconfig.consumer.json)
is all a consumer must set, and `yarn check` compiles the example under it: `strict`;
`moduleResolution: bundler`, since the runtime's imports name no extension, and a bundler to run
them, esbuild here; and the libraries `ESNext.Iterator`, `ESNext.Disposable` and `DOM`. The C# half
needs none of it: a project or a package compiles the runtime under its own rules.
